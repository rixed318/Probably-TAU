# Правила для кодовых агентов и независимых чатов

## Источник истины
Перед любой реализацией обязательно прочитать:
1. `README.md` — статус и навигация.
2. `docs/GDD.md` — полный исходный GDD v0.1.
3. `docs/DECISIONS.md` — утверждённые и открытые архитектурные решения.
4. `docs/ARCHITECTURE.md`, `docs/MECHANICS.md` — проектные границы.
5. `docs/CHAT_WORKFLOW.md` — зоны ответственности, интеграция и handoff.

В споре: **явное актуальное решение владельца > DECISIONS > принятый PR > GDD > предложения агента**. Не выдавать предложения из GDD за окончательные решения.

## Необходимые ограничения
- Использовать Unity 6 LTS + C#, PC/Windows, одиночный 2D-проект.
- Чужую игру Probably Stolen использовать только как референс по геймдизайну. **Нельзя копировать** её исходники, ассеты, тексты, интерфейсы, персонажей или характерные элементы оформления.
- Сеттинг ТАУ — художественный. Не приписывать реальной Академии вымышленные финансовые показатели, инциденты, нарушения или реальные реплики конкретных людей.
- До согласования не добавлять платный контент, рекламу, сетевые сервисы или сторонние SDK.
- Simulation/Core не зависит от UnityEngine. Unity API только в адаптерах/Presentation. ScriptableObject — конфигурация, не mutable state прохождения.
- Денежные значения в целых единицах (предпочтительно целое число копеек/игровых единиц с единообразным форматом). Не использовать float для финансов.
- Весь мутирующий геймплей через валидируемые команды. Не изменять GameState напрямую из UI.
- Каждому экземпляру сущности — стабильный ID. Сохранения — versioned snapshot + миграции.
- Случайность — явный seed и сохраняемое состояние PRNG; логика воспроизводима после загрузки.
- Экономические операции атомарны, сохраняется ledger.
- Изменения игрового баланса без тестов и обоснования не принимать.

## Работа в параллельных ветках
- Один чат = одна подсистема / Issue / ветка `feature/<area>-<issue>`.
- Никогда не работать прямо в `main`, кроме утверждённых документационных изменений.
- Перед изменениями проверить текущую ветку и последний commit, существующие файлы и актуальные Issues.
- Не переписывать файлы, принадлежащие другому чату, без координации.
- Контракты между подсистемами документировать до реализации.
- Не добавлять package dependencies без объяснения и одобрения.
- Каждой задаче: цель, in/out of scope, acceptance criteria, тесты, handoff.
- Открыть PR; не сливать чужие ветки самостоятельно.

## Минимальные критерии качества
- Проект собирается и не содержит compile errors.
- Корректное восстановление состояния из сохранения; отсутствие дублирования денег/событий.
- Детерминированные тесты для правил экономики и событий.
- Нет жёстких строк UI в бизнес-логике.
- Публичные методы с устойчивыми контрактами и ясными названиями.
- Любой результат работы сопровождается названием ветки, SHA, списком файлов, тестами, рисками и дальнейшим шагом.

## Handoff после каждого чата
Создать или обновить `docs/handoffs/<area>.md`:
- Цель, Issue, ветка, commit/PR.
- Что сделано; что НЕ сделано.
- Принятые решения и изменённые публичные контракты.
- Как проверить вручную и автоматически.
- Известные проблемы; зависимые задачи.

Если файла/ветки ещё нет — не заявлять, что код уже реализован.
