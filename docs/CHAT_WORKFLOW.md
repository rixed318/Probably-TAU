# Работа в нескольких чатах без потери контекста

## Главный принцип
**GitHub — источник истины; чат — рабочая сессия.** Новый чат не обязан помнить предыдущие диалоги. Каждый начинает с чтения последних документов, Issues и веток.

## Разделение чатов
| Чат | Область | Владеет | Не должен менять без согласования |
|---|---|---|---|
| 00 — Продюсер/интеграция | GDD, приоритеты, roadmap, PR review | `docs/`, GitHub Issues | Код подсистем |
| 01 — Simulation Core | GameState, время, команды, экономика | `Runtime/Core/`, `Runtime/Application/` | Визуальный UI, тексты |
| 02 — Посетители и сюжет | NPC, события, переговоры | NPC/Event logic + data specs | Экономические контракты |
| 03 — UI/UX | Кабинет, документы, экраны, анимации | `Runtime/Presentation/` | GameState/Core |
| 04 — Контент и баланс | Карточки заявок, проекты, сложности | `Content/`, сценарные данные | Engine/runtime |
| 05 — QA/сохранения | Сериализация, регрессии, тесты | `Infrastructure/`, `Tests/` | Правила баланса без PR |

Папки — целевая структура; пока Unity-проекта нет. Первый интеграционный шаг определит точные границы и asmdef.

## Открывающий промпт для любого нового чата
```text
Мы разрабатываем Probably-TAU — оригинальную 2D-игру «ТАУ: Президент Академии» на Unity 6/C#.
Репозиторий: https://github.com/rixed318/Probably-TAU

Твоя роль: [указать один чат/подсистему из docs/CHAT_WORKFLOW.md].
Сначала через GitHub прочитай README.md, AGENTS.md, docs/GDD.md,
docs/DECISIONS.md, docs/ARCHITECTURE.md и актуальные Issues/ветки.
Не считай память чата источником истины и не переписывай чужие подсистемы.
Предложи план строго в своей области, затем работай в feature-ветке,
создавай PR, тесты и docs/handoffs/<area>.md.
Не сливай PR в main без моего явного разрешения.
Если код ещё не создан — не утверждай обратного.
```

## Один Issue — одна задача
**Шаблон описания:** зачем → границы in/out → файлы/контракты → критерии готовности → тесты → зависимость. Указывайте ID Issue в коммите/PR. Каждый чат сначала проверяет, не ведётся ли уже эта работа.

## Интеграция
1. Чат-системщик фиксирует интерфейсы/события до UI/контента.
2. Параллельные чаты обсуждают изменения контракта через Issue или ADR.
3. Каждый сдаёт PR и handoff.
4. Интеграционный чат проверяет PR, тесты, конфликты и обновляет статусы.
5. В `main` попадает только согласованная и проверенная работа.

## Если контекст утрачен
Прочитать репозиторий и последний handoff нужной подсистемы. Не восстанавливать архитектуру по догадкам, не полагаться только на предыдущее сообщение.
