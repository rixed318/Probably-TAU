# Работа в нескольких чатах без потери контекста

## Главный принцип
**GitHub — источник истины; чат — рабочая сессия.** Новый чат не обязан помнить предыдущие диалоги. Каждый начинает с чтения последних документов, Issues и веток.

## Разделение чатов
| Чат | Область | Владеет | Не должен менять без согласования |
|---|---|---|---|
| 00 — Продюсер/интеграция | GDD, приоритеты, roadmap, PR review | `docs/`, GitHub Issues | Код подсистем |
| 01 — Simulation Core | GameState, время, команды, экономика | `Runtime/Core/`, `Runtime/Application/` | Визуальный UI, тексты |
| 02 — Посетители и сюжет | NPC, события, переговоры | NPC/Event logic + data specs | Экономические контракты |
| 03 — UI/UX | Кабинет, документы, экраны, анимации | `Runtime/Presentation/` | GameState/Core |
| 04 — Контент и баланс | Карточки заявок, проекты, сложности | `Content/`, сценарные данные | Engine/runtime |
| 05 — QA/сохранения | Сериализация, регрессии, тесты | `Infrastructure/`, `Tests/` | Правила баланса без PR |

Папки — целевая структура; пока Unity-проекта нет. Первый интеграционный шаг определит точные границы и asmdef.

## Открывающий промпт для любого нового чата
```text
Мы разрабатываем Probably-TAU — оригинальную 2D-игру «ТАУ: Президент Академии» на Unity 6/C#.
Репозиторий: https://github.com/rixed318/Probably-TAU

Твоя роль: [указать один чат/подсистему из docs/CHAT_WORKFLOW.md].
Сначала через GitHub прочитай README.md, AGENTS.md, docs/GDD.md,
docs/DECISIONS.md, docs/ARCHITECTURE.md и актуальные Issues/ветки.
Не считай память чата источником истины и не переписывай чужие подсистемы.
Предложи план строго в своей области, затем работай в feature-ветке,
создавай PR, тесты и docs/handoffs/<area>.md.
Не сливай PR в main без моего явного разрешения.
Если код ещё не создан — не утверждай обратного.
```

## Один Issue — одна задача
**Шаблон описания:** зачем → границы in/out → файлы/контракты → критерии готовности → тесты → зависимость. Указывайте ID Issue в коммите/PR. Каждый чат сначала проверяет, не ведётся ли уже эта работа.

## Интеграция
1. Чат-системщик фиксирует интерфейсы/события до UI/контента.
2. Параллельные чаты обсуждают изменения контракта через Issue или ADR.
3. Каждый сдаёт PR и handoff.
4. Интеграционный чат проверяет PR, тесты, конфликты и обновляет статусы.
5. В `main` попадает только согласованная и проверенная работа.

## Если контекст утрачен
Прочитать репозиторий и последний handoff нужной подсистемы. Не восстанавливать архитектуру по догадкам, не полагаться только на предыдущее сообщение.

## Координация и порядок интеграции — решение 14.11.2026
**Чат 00 = текущий главный чат пользователя.** Он отвечает за общие контракты, приоритеты, архитектурные решения, review и разрешение на merge в `main`. Чат 05 — независимое QA/сохранения; он НЕ является объединителем всех веток.

### Что можно начать параллельно
- **01 Core:** создать Unity 6 LTS проект и отдельно лежащее Core API; первым делом предложить базовые контракты. Пока не создавать UI/NPC контент.
- **03 UI:** начать с wireframe/временных макетов кабинета, карточки заявки и дневного отчёта. Использовать mock data; не ссылаться на несуществующие runtime-классы.
- **04 Content:** подготовить дизайн и проверяемые документы 12 событий, 3 типов заявок, 2 проектов. Пока не коммитить несовместимые ScriptableObject assets, пока нет content schema.
- **02 NPC:** уже можно проектировать генерацию посетителей, события и интерфейсы, но интегрируемый runtime-код — после утверждения Core/GameState/contracts.
- **05 QA/Save:** уже можно подготовить тест-план, инварианты и versioned save schema, но actual SaveService после стабилизации GameState.

### Gate C0: обязательные контракты
До интеграции NPC/UI и сохранений чат 01 предлагает, а чат 00 фиксирует в документации: versioned GameState, IDs, деньги/units, GameClock/AdvanceDay, CommandProcessor, domain events, PRNG seed/state, interfaces queries, сериализуемая модель. UI допускается разрабатывать параллельно только через mocks, Content — только как сценарные документы. Изменения контрактов — отдельный PR/ADR.

### Git + PR pipeline
```text
main (стабильная база)
 ├── feature/core-2
 ├── feature/ui-5
 ├── feature/content-7
 ├── feature/npc-4
 └── feature/save-6
          ↓
Каждый чат коммитит/пушит только в свою ветку
          ↓
Pull Request → проверки, ревью координатора 00, QA 05
          ↓
При необходимости обновление ветки от main, исправление конфликтов автором
          ↓
Только с явным одобрением владельца: merge PR в main
          ↓
Следующие ветки основаны на обновлённом main
```

**Не выполнять:** прямые коммиты в `main` от feature-чатов; слияние нескольких независимых веток в одну без review; автоматическое включение изменений без тестов; перезапись чужих файлов.

**Критерии слияния:** понятный diff; указан Issue; контракты не нарушены; существующие проверки зелёные; автор перечислил что проверял и что не проверял; разработчик и координатор согласовали затрагиваемые подсистемы. Перед сложными merge QA 05 изучает PR, проверяет интеграционные инварианты, но merge выполняет 00 только после разрешения пользователя.

### Ограничения чатов
Отдельные разговоры не продолжают работу автономно и не синхронизируют незаписанные решения друг друга. GitHub Issue, PR и handoff — единственный обязательный механизм передачи статуса. Перед каждым шагом проверять актуальный `main` и последние коммиты.
